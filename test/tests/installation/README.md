# Installation test instructions and expected outcomes

These four cases check application initialization, object registration, data
access, material coupling, solver execution, and output generation. Passing them
confirms that these execution paths work in the tested environment; it does not
validate the physical models, their calibration, or numerical accuracy.

## Prerequisites

Build `ml-opt` and activate the same compatible MOOSE environment used for the
build. The output checker requires Python 3 and only its standard library.
All meshes are generated by the inputs; the two CSV fixtures are bundled here.
The original `kuhn.i` and `vp_T300.i` files are not runtime dependencies.

For the reviewed Negishi installation:

```bash
module load conda
conda activate moose
module unload openmpi/4.1.4
export MOOSE_DIR="$HOME/projects/moose"
cd ~/projects/ml
```

These environment commands are site-specific. This installation uses MPICH;
loading the site's OpenMPI alongside it caused startup failures during testing.

## Run the complete suite

From `~/projects/ml`:

```bash
./run_tests --re installation -j 2
```

Expected summary: **8 passed, 0 skipped, 0 failed**. There are four simulation
entries and four dependent output checks in [tests](tests). Each simulation runs
with one MPI process and one thread; `-j 2` allows two harness jobs concurrently.
Each simulation entry has a 120-second time limit.

To run only one case and its output check, filter by its basename, for example:

```bash
./run_tests --re 'installation.*mode1_fracture' -j 1
```

Expected summary for that command: **2 passed, 0 skipped, 0 failed**.

## Run cases manually

All per-case commands below assume this working directory:

```bash
cd ~/projects/ml/test/tests/installation
```

Run the checker only after the simulation exits successfully. A checker reads
existing CSV output; running it alone can inspect stale results. The harness
handles the simulation/check dependency automatically.

Each input writes `<case>_out.csv` and `<case>_out.e` in this directory. The CSV
contains scalar diagnostics; open the Exodus `.e` file in ParaView to inspect
fields. Repeat runs reuse these output names. Checkpoint directories may also
be created by MOOSE.

## 1. PBX microstructure initialization

Input: [pbx_initialization.i](pbx_initialization.i).

```bash
../../../ml-opt -i pbx_initialization.i --error --error-unused
python3 check_outputs.py pbx_initialization
```

The input creates a 12×12 mesh, generates four particle centers, assigns
particle/binder identifiers and orientation fields, and initializes the fraction
field using synthetic data. [fractions.csv](fractions.csv) and
[pore_fractions.csv](pore_fractions.csv) are single numeric rows without headers.
Run from this directory because the custom reader resolves filenames relative
to the working directory.

**Expected outcome:** initialization completes and stops at time zero. No
nonlinear timestep solve is performed: `num_steps = 0`. The console may show
`Time Step 0`, but must not show `Time Step 1`.

The automatic check requires:

- Exactly one CSV data row at `time = 0`.
- A positive `max_grain` and `min_grain = 0`, indicating particles and binder.
- `mean_fraction` strictly between zero and one.

Expected checker message:

```text
PASS: pbx_initialization (1 output rows)
```

For visual inspection, plot `grainID`, `density_i`, `Y1`, and `euler1`–`euler3`.
`density_i` holds the microstructure identifiers used by this setup; it should
not be interpreted as a physical density field. No chemistry or mechanics is
advanced. This checks generation during initialization, not the separate Python
input-generation utility.

## 2. AD thermal diffusion

Input: [ad_thermal_diffusion.i](ad_thermal_diffusion.i).

```bash
../../../ml-opt -i ad_thermal_diffusion.i --error --error-unused
python3 check_outputs.py ad_thermal_diffusion
```

The input initializes a seeded random temperature field between 290 and 310 on
an 8×8 mesh. AD heat-capacity and conduction kernels evolve it with insulated
boundaries and synthetic constant properties. There is no mechanical coupling.
**This is a nonreactive diffusion test; thermal-decomposition kinetics are not
included.**

**Expected outcome:** five converged steps of size 0.01, ending at `time = 0.05`.
The temperature field becomes smoother and its maximum–minimum range decreases.
The insulated constant-property setup should also preserve the mean temperature
to solver precision, though mean conservation is not asserted by the checker.

The automatic check requires:

- Six CSV data rows, including the initial state, ending at time 0.05.
- A nonuniform initial field (`max_temperature > min_temperature`).
- A smaller temperature range at the final time than at the initial time.

Expected checker message:

```text
PASS: ad_thermal_diffusion (6 output rows)
```

Plot `temperature` in Exodus, or plot `min_temperature`, `max_temperature`, and
`mean_temperature` against time from the CSV.

## 3. Mode-I fracture coupling

Input: [mode1_fracture.i](mode1_fracture.i), adapted from `kuhn.i`.

```bash
../../../ml-opt -i mode1_fracture.i --error --error-unused
python3 check_outputs.py mode1_fracture
```

The input uses an 8×8 mesh with a horizontal diffuse notch, finite-strain
mechanics, `ADElastoPlastic`, degradation/history energy, and AD Allen–Cahn
kernels. The top boundary moves vertically while the bottom is fixed vertically;
the left edge is constrained horizontally. Opening is normal to the notch.
Old-value lower bounds on damage and an upper bound of one prevent healing and
limit damage using PETSc's variational-inequality solver.

**Expected outcome:** five converged steps of size 0.02, ending at `time = 0.1`.
The top displacement reaches 0.005, and the initially nonzero damage field
evolves. A coarse, short integration test is not expected to produce a resolved
crack path or complete specimen separation.

The automatic check requires:

- Six CSV data rows, including the initial state, ending at time 0.1.
- Positive final `opening` and positive initial `mean_damage`.
- Final `mean_damage` greater than its initial value.
- All reported mean-damage values between zero and one.

Expected checker message:

```text
PASS: mode1_fracture (6 output rows)
```

Inspect `c`, displacement, and available stress/history fields in Exodus. The
checker evaluates mean damage; it does not independently check nodal damage
bounds, crack geometry, or fracture-energy balance.

## 4. Single-element viscoplastic relaxation

Input: [viscoplastic_relaxation.i](viscoplastic_relaxation.i), adapted from
`vp_T300.i`.

```bash
../../../ml-opt -i viscoplastic_relaxation.i --error --error-unused
python3 check_outputs.py viscoplastic_relaxation
```

One QUAD4 element uses the NH viscoplastic branch at a fixed temperature of 300.
The right-edge displacement ramps from zero to 0.01 over 20 time units, then
remains at 0.01 until time 200. Damage evolution kernels are inactive to isolate
constitutive relaxation. The input retains illustrative reference properties
and uses serial LU without requiring MUMPS.

**Expected outcome:** with the configured one-unit timestep, 200 accepted steps
and 200 CSV rows. Only accepted timestep ends are output, so there is no initial
CSV row. During the hold, displacement stays fixed, accumulated viscoplastic
strain continues increasing, and axial stress decreases.

The automatic check requires:

- Completion at time 200 and an output sample at the ramp endpoint, time 20.
- `right_displacement` approximately 0.01 for all hold samples.
- Final `mean_vp_ep` greater than its positive value at time 20.
- Final `mean_vp_sigma_xx` less than its value at time 20.
- Positive `mean_vp_Je` and `mean_vp_Jp` throughout the output.

Expected checker message for the configured run:

```text
PASS: viscoplastic_relaxation (200 output rows)
```

The checker does not require exactly 200 rows if timestep cutbacks occur, but it
does require the ramp-end sample and final time. Plot `right_displacement`,
`mean_vp_sigma_xx`, `mean_vp_ep`, and `mean_vp_ep_dot` against time to inspect the
ramp and relaxation stages.

## Shared pass criteria and failure diagnosis

[check_outputs.py](check_outputs.py) also requires nonempty CSV output, finite
values in every column, and strictly increasing times when multiple rows exist.
A successful check prints `PASS` and exits with code zero. Simulation completion
alone is insufficient: its dependent output check must pass too.

| Symptom | What to check |
| --- | --- |
| `ml-opt` missing or cannot load libraries | Build the application and activate its compatible runtime environment. |
| MPI/VTK startup error or invalid communicator | Check for mixed MPI installations; use the documented Negishi environment setup where applicable. |
| Unknown object or missing material property | Confirm the executable was built from the intended source and with the required MOOSE modules. |
| Cannot open CSV file | Run from this directory and retain both fixture CSVs. |
| Missing output, `NaN`, or failed output assertion | Inspect the simulation error and convergence log before interpreting the CSV. |
| Test timeout | Check compilation/JIT startup costs and solver progress; a timeout is not a passing installation result. |
| Fracture completes without a clear advancing crack | This case checks coupling and field evolution on a coarse mesh, not resolved propagation. |

These checks were exercised with the existing executable during test creation.
Rebuild and rerun after source or dependency changes. Expected trends and
execution signatures are the acceptance criteria; precise numerical values are
not stored as physical-validation reference results.
